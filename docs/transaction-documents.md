# Transaction evidence: architecture, operations and verification

## Repository discovery

- Backend: Express 5, CommonJS, Prisma 5.22/PostgreSQL. Routes mounted at `/api/v1`. JWT Bearer authentication, database role permissions, operational JSON errors.
- Frontend: Next.js 16 App Router, React 19, Tailwind 4, lucide icons. Forms use fetch/`API_URL`; shared `apiRequest` is available. The API proxy currently converts binary data to text and must be corrected.
- No upload/storage/scanning implementation exists. `Expense.attachment`, property `documents`, and customer `kycDocuments` are legacy metadata fields, not a secure upload system.
- Wallet/office expenses share `Expense`; customer collections use `CustomerPayment`; refunds use `CustomerPayment.status=REFUND_DISBURSED`; land payouts use `PropertyPayment`; bank inflows use `WalletTransaction.referenceType=BANK_STATEMENT`. Property legal documents remain a separate source.
- Journals reference originating records; older expense references use `EXP-` plus eight UUID hex characters. Ambiguous legacy references must not be guessed.
- Existing audit helper accepts a transaction but swallows errors. Evidence mutations will require a successful audit result before commit.
- Existing idempotency middleware is response caching, not an atomic reservation, and does not scope replay to actor/endpoint. Document uploads use database uniqueness and actor-bound fingerprints instead of inheriting that weakness.
- Notifications are computed by `notificationController`; review queue indicators can use document counts without introducing financial notifications.
- There is no Prisma migration history. README/CI use `prisma db push`. Ship an additive SQL upgrade and an explicit deployment command, never run schema changes against the configured database automatically.

## Implementation map

1. `services/documents`: file validation, provider abstraction, source authorization, policy, version lifecycle and transaction attachment.
2. `TransactionDocument`, `DocumentUpload`, and `DocumentException`: additive schema and SQL upgrade; no payroll or journal table changes.
3. `/api/v1/documents`: actor-bound staging, source lists/policy, review, authorized content, verification/rejection/replacement/archive, exceptions, journal resolution.
4. Existing create controllers attach staged evidence inside their existing transactions. Required expense receipts or reasoned exceptions are checked server-side.
5. `TransactionDocuments`, evidence detail dialog, and centralized review page, integrated into expense/payment/inflow/payout/refund forms and existing detail views.
6. Tests and release checks; document production configuration and limitations honestly.

## Policy assumptions

Expense receipts are required for new submissions by default. A reasoned exception is pending until reviewed by Accounting/Admin; it does not imply approval. Existing financial posting remains immediate, because the application has no pending-expense accounting state. Other payment proofs and cheque front images are recommended by default, configurable as required. Cheque back images are optional. No high-value threshold is invented. No receipt, invoice or official receipt is generated by uploading customer proof.

## Architecture and financial invariants

`TransactionDocument` is immutable file evidence, `DocumentUpload` is an expiring actor-owned staging record, and `DocumentException` records a reasoned missing-receipt request. Financial tables and debit/credit algorithms remain authoritative and unchanged.

1. The client sends raw file bytes to the authenticated staging endpoint with a unique idempotency key. The engine validates extension, MIME, signature, decoded contents, size and SHA-256, runs the optional scanner, writes an opaque private object and audits a staging record.
2. Existing expense/payment/inflow/payout/refund requests include `documentUploadIds`. The controller claims those intents and creates evidence **inside its existing financial database transaction**. Failed receipt policy, audit, UTR, treasury or accounting-period checks roll back the evidence claim and financial writes together. The immutable staged bytes remain available for retry until expiry.
3. Documents begin as `PENDING_REVIEW`. Only authorized Accounting/Admin reviewers can verify or reject. Rejection requires a reason. Replacement creates a new version linked by `replacesDocumentId` and `rootDocumentId`; the old row becomes `REPLACED`, retaining its rejection/verification details and bytes. Archival is an audited Admin action, not deletion.
4. Preview/download perform fresh authentication, current database permissions, source-record authorization, cheque restrictions and content-hash validation on every request. Verification also checks the stored bytes before accepting evidence.

The polymorphic source relation is intentionally **not** represented as a database foreign key. `sources.js` resolves actual records, checks UUIDs/module identity and ownership/team/global permissions for every operation. User and version relations do use restrictive foreign keys. Unrelated modules must not hard-delete financial source records; retained documents whose source no longer exists fail closed rather than exposing evidence.

Advisory locks serialize same-source duplicate hashes and per-user staging quotas. Conditional updates and database uniqueness enforce single-consumption uploads, single-successor replacement and single-winner reviews. Stage replay is scoped by actor and bound to file metadata/hash/module/type. These protections do not replace or broaden the existing financial endpoint idempotency implementation.

| Source | Authoritative record | Integration |
| --- | --- | --- |
| `EXPENSE` | `Expense` (office and wallet expenses) | Four-section expense form; expense list evidence |
| `CUSTOMER_PAYMENT` | `CustomerPayment`, excluding refunds | Collection form and customer statement |
| `BANK_INFLOW` | `WalletTransaction` with `BANK_STATEMENT` reference | Bank inflow form and treasury inflow list |
| `LAND_PAYOUT` | `PropertyPayment` | Payout form and payout history |
| `REFUND` | `CustomerPayment.status=REFUND_DISBURSED` | Cancellation settlement form and statement |
| `PROPERTY` | `PropertyAcquisition` | Separate **Legal documents** action; never mixed with payout proof |
| `WALLET_ALLOCATION` | Allocation/transfer `WalletTransaction` | Wallet ledger evidence action and review center |
| `OTHER_FINANCIAL_TRANSACTION` | Adjustment/reversal `WalletTransaction` | Wallet ledger evidence action and review center |

The review center is `/dashboards/documents`, exposed in the dashboard hub navigation for authorized finance reviewers. It offers pending/verified-today/rejected/missing counts, transaction-aware filters, source lists, SHA-256 duplicate investigation and configurable high-value filtering. Existing records are not silently grandfathered as documented: missing receipt policy is visible without rewriting them.

`TransactionDocuments` handles staged/attached modes, drag/drop, validation, progress, idempotent retry, local staged preview, removal before submission, authorized saved preview/download, review reasons, replacement and history. Source lists paginate at 50 versions; policy state is calculated across **all** versions, not just that page. Review results paginate at 20 by default (maximum 100).

The General Ledger resolves evidence through its journal's original source. Short legacy expense references and allocation references are accepted only when unambiguous. Refund journals containing only a customer ID return no source when multiple refund records exist; no evidence is guessed or duplicated on journal lines. Journals without an implemented source mapping display an explicit no-unambiguous-source message.

Wallet allocation/adjustment evidence is attached to the completed transaction through its detail action. Their existing allocation/approval forms and posting rules have not been rewritten. Cheque instrument metadata remains in the existing transaction fields; front/back are restricted evidence types, not a separate cheque accounting system.

## API contract

All paths below are under `/api/v1/documents`, use existing JWT Bearer authentication, and return the application's JSON `success` envelope except binary content responses.

| Method/path | Purpose |
| --- | --- |
| `GET /policy?sourceType=...&paymentMode=...` | Central types, required groups and file limits; accepts either `document.upload` or `document.view` for new-transaction forms |
| `POST /uploads?sourceType=...&documentType=...&fileName=...` | Raw bytes, matching `Content-Type`, `Idempotency-Key` required; optional `sourceId` for an existing accessible source |
| `POST /uploads/:id/discard` | Discard actor's unclaimed intent; cleanup removes bytes later |
| `GET /?sourceType=...&sourceId=...&page=1` | Source info, evidence, permissions, policy and exception state |
| `POST /` | Attach `{sourceType, sourceId, uploadIds}` to an existing accessible source |
| `GET /:id` | Metadata, version lineage and latest 100 lifecycle audit events |
| `GET /:id/preview`, `GET /:id/download` | Authorized, no-store content; no storage path exposed |
| `POST /:id/verify`, `/reject`, `/archive` | Review action; `{reason}` required for reject/archive |
| `POST /:id/replace` | `{uploadId}` of a newly staged same-type replacement |
| `POST /exceptions/:id/verify`, `/reject` | Finance review with mandatory `{reason}` |
| `GET /review` | Evidence queue |
| `GET /transactions` | Financial sources, optionally `missing=true` |
| `GET /summary` | Dashboard indicators |
| `GET /journal/:id` | Resolve an authorized source transaction |

Review filters: `sourceType`, `sourceId`, `documentType`, `status`, `utr`, `search`, `customerId`, `propertyId`, `employee` (creator user ID), `uploadedBy`, `paymentMode`, `from`, `to`, `minAmount`, `maxAmount`, `sha256`, `page`, `pageSize`. Values are bound SQL parameters. Document-only filters apply to the review queue, not source-only lists. Dates filter transaction dates; verified-today uses IST. Some legacy wallet `createdBy` values are emails, so use search when a legacy creator ID filter is not applicable.

Errors use 400 validation, 401 authentication, 403 access, 404 source/document absent, 409 conflicting/concurrent action, 410 expired replay, 413 size, 429 staging/rate limit, and 503 missing/corrupt private storage or mandatory audit/scanner failures. Financial controller response conventions remain unchanged.

## Permissions and security

New permissions: `document.view`, `document.upload`, `document.download`, `document.replace`, `document.review`, `document.sensitive`, `document.archive`.

If an existing user's form says `Access denied: Requires document.view`, the deployed backend may still have the earlier policy-route gate or the role grants may not have been synchronized. Deploy the updated route, then run `node scripts/sync_document_permissions.js` **against the intended database only after confirming its identity and the additive schema upgrade**. This is a database write; it is not performed automatically at app startup. Upload authorization still requires `document.upload` and source/module access; making policy readable does not bypass those checks.

Existing employee/manager roles receive the first four, bounded by actual source access. Accounting additionally receives review and sensitive-cheque access. Admin additionally receives archival. Review/archive are also restricted to finance roles even if an employee is accidentally granted the permission. Every document HTTP request refreshes current role grants and active-account status from the database; stale JWT claims cannot preserve revoked document privileges.

Files: PDF/JPEG/PNG/WEBP only, 10 MB per file, at most five files in one submission, 30 unclaimed live intents per actor, and 12 uploads/minute/IP per process. Shared multi-instance deployments should enforce an equivalent global gateway limit. PDFs are parsed, limited to 200 pages, and reject encryption and active/embedded action dictionaries (including nested objects). Images are fully decoded with a 25-megapixel cap; previews are re-encoded WebP. This is format hardening, **not an antivirus guarantee**.

Local objects use immutable random keys, restrictive filesystem permissions, no public route, and no original filename in the path. Downloads have safe disposition, `nosniff`, no-store and sandbox headers. PDF previews use a sandboxed iframe; browsers that disable their PDF viewer there can download the authorized original. There are **no signed URLs to expire** with this provider: every content request is authorized instead, and expired-token denial is tested.

Same-source identical hashes are rejected explicitly; cross-transaction reuse remains traceable with hash filtering. Content is not placed in audit logs. Upload, attachment, verify, reject, replace, archive, exception review, preview and download events use the existing audit model. Evidence-changing operations fail/roll back if audit creation fails. The application-wide audit viewer retains the complete audit stream beyond the latest 100 shown in a detail response.

## Production configuration and deployment

No migration, permission sync or financial operation was executed against the configured/live database during development. Local verification used disposable localhost PostgreSQL clusters. Deploy the backend/database before exposing the new frontend.

1. Back up the intended database. For local-directory storage, provision a durable **private** directory outside public/static/frontend web roots and grant only the backend service account access. For S3-compatible storage, provision a private bucket and bucket-scoped credentials. Encrypt storage and backups according to your operational policy.
2. Configure one private storage provider. Development may omit `DOCUMENT_STORAGE_PROVIDER` and use the ignored `backend/private-documents` folder. For Hostinger managed Node production, use `DOCUMENT_STORAGE_PROVIDER=s3` with a dedicated private S3-compatible bucket and the `DOCUMENT_S3_*` variables below. The bucket must have no public access. Production fails closed when the selected provider is misconfigured. The server retains file bytes in the selected provider; the database stores only opaque keys and metadata. Local development and production must use distinct Neon databases and distinct storage. Never switch a database from local to S3 while it has local-backed document rows without first copying those exact object keys to the bucket and verifying `npm run documents:reconcile` reports `unavailable: 0`.
3. Review and apply `backend/prisma/upgrades/20260930_transaction_documents.sql`. It adds only `TransactionDocument`, `DocumentUpload`, `DocumentException`, their indexes and restrictive relations. Because this repository had no Prisma migration history, this is an explicit additive upgrade—not a fictitious `migrate deploy` history. Run from `backend`: `node scripts/deploy_document_schema.js --apply`. The runner applies it transactionally, uses an advisory lock and a five-second lock timeout, and refuses pre-existing document tables. Rehearse on a restored staging backup first.
4. With application processes stopped, run `npx prisma generate`, then `node scripts/sync_document_permissions.js`. The dedicated sync adds only document grants; it does not seed users or alter unrelated permissions. Do **not** run the development seed against production. Restart backend and have users refresh their session to refresh navigation visibility.
5. Perform a clean frontend dependency install from the committed lockfile and verify the installed Next.js and Sharp versions before building/deploying. The Next API proxy now streams binary request/response bodies instead of converting them to text. Document requests allow a 120-second proxy timeout. Configure upstream proxy body limits/timeouts to accommodate 10 MB files and scanning. Direct-backend CORS must allow `Authorization`, `Content-Type` and `Idempotency-Key` (already present in this app).
6. Smoke-test upload → financial submit → finance review → download with separate test roles on staging. Verify storage persistence across restart and coordinated database/filesystem restore before production rollout.

Use `backend/.env.documents.example` as the host configuration template. The backend now includes a ClamAV `INSTREAM` adapter (`DOCUMENT_SCANNER_PROVIDER=clamav`) and a read/write/remove plus scanner health preflight: run `npm run documents:check` **on the backend host** before enabling uploads. Keep the ClamAV TCP listener on loopback or a private network, with `StreamMaxLength` above 10 MB and current signatures. A daemon is not bundled with the application; this workstation has no ClamAV listener, so a live malware scan has not been claimed. Production/Passenger uploads fail closed without a configured scanner and explicit private storage path. The private storage path must be a host-provided persistent directory outside deployed/public files; a repository-local development folder is not a production volume. Back up evidence objects together with database records.

For Hostinger managed Node apps, do not put evidence under `hbuilds/current/nodejs` or `public_html`: those are deployment/public locations. Create a dedicated private S3-compatible bucket (Cloudflare R2 or AWS S3), configure its endpoint/region and bucket-scoped credentials in backend environment variables, then run `npm run documents:check` from the backend runtime. The bucket token needs object read/write/delete plus list permission for preflight and reconciliation, scoped to this bucket only. The application never issues public or presigned file URLs: it retrieves objects server-side only after the existing actor/source/permission checks. Keep bucket public access disabled, restrict the token to that bucket, protect credentials, and configure bucket backups/retention. The existing ClamAV requirement is independent of the bucket; if the managed plan cannot reach a trusted private scanner, uploads remain disabled. Localhost uses ignored `backend/private-documents` by default with its separate development Neon database.

`npm run documents:backup` creates a custom-format `pg_dump` under ignored `backend/backups` and validates it with `pg_restore --list`. Set `DOCUMENT_PG_BIN` to compatible PostgreSQL client binaries; on Windows, set `DOCUMENT_PG_CA_BUNDLE` to a trusted CA bundle if `sslrootcert=system` is unavailable. Restrict the backup ACL and keep an encrypted off-host copy; the dump contains sensitive financial data. On 2026-10-01, the configured Neon PostgreSQL 18.6 database was backed up, the additive document upgrade applied, and seven document permission codes synchronized. Read-only verification found all three tables and role grant counts Admin 7, Accounting 6, and Manager/Marketing/Other/Sales 4 each. This database work does not configure Hostinger's storage or scanner or prove that its runtime uses this same database.

The bundled ClamAV adapter speaks the `INSTREAM` protocol, but the ClamAV daemon/signatures are external host infrastructure and are **not installed or claimed active**. Enable the provider and required flag only when that daemon is reachable. Module paths are server configuration, never request-controlled. The private S3 provider is implemented; no bucket, live credentials, public bucket or signed URL service is claimed to exist.

Receipt exceptions require 10–1000 characters and retain requester/time/reviewer/reason. Approval waives only the expense receipt group, never an independently required bank proof or cheque front. Changing central policy can flag historical transactions as missing; it does not rewrite or reverse their financial entries.

## Cleanup, retention and recovery

Run `npm run documents:reconcile` for a dry run, inspect counts, then `npm run documents:reconcile -- --apply` in an approved operations job. It removes only expired/discarded **unclaimed** files and orphan objects older than 48 hours, and reports missing retained evidence with a nonzero exit code. The grace period avoids deleting files with uncertain commit outcomes. Claims/discards are conditional updates to prevent cleanup racing a financial commit. Staging metadata/audits remain for replay and investigation. Uploaded intents expire after 24 hours.

Linked, rejected, replaced and archived evidence is never purged by this job. No legal retention period was invented. Database backups and private objects must be backed up/restored consistently; source-level visibility still requires live source records. Decide retention, backup encryption, scanner and storage capacity with the operations owner before production activation.

Rollback is application-first: stop new submissions, retain all document tables/files/audits and roll back application code. There is deliberately no destructive down-migration that erases financial evidence. Before first usage only, an operator may remove the three empty tables in dependency order after a verified backup; this is not automated. Do not drop populated evidence tables to undo a deployment.
